FINTECH ARCHITECTURAL SPECIFICATION

Vault Architecture, Four-Eyes Governance & Network Isolation

A deep-dive technical paper explaining why PortGrid introduced cryptographic vaulting, the mathematical foundations of authenticated AES-256-GCM envelope encryption, dual-control Maker-Checker policies, and kernel network namespaces.

1 Why PortGrid Vault Was Introduced (The Threat Model)

In standard development environments, credentials (database passwords, API tokens, JWT private signing keys) suffer from four systemic vulnerabilities known as Secret Sprawl:

VULNERABILITY A: PLAIN-TEXT LEAKAGE

Traditional Docker Compose files and local .env files store master passwords in unencrypted plain text on disk. These files are routinely committed to public git repositories by accident or indexed by local search processes.

VULNERABILITY B: DOCKER INSPECT EXPOSURE

When passwords are passed via standard container environment variables (-e POSTGRES_PASSWORD=...), any unprivileged process with Docker socket access can execute docker inspect to dump every secret in plain text.

VULNERABILITY C: ROGUE VOLUME DESTRUCTION

A single developer mistake running destructive teardowns or purges instantly wipes critical local test databases or replication sets without team oversight or cryptographic record.

VULNERABILITY D: BROAD LAN EXPOSURE

Binding ports to 0.0.0.0 exposes local test databases (PostgreSQL, MongoDB, Kafka) to every machine on the same public coffee shop Wi-Fi or corporate office network.

PortGrid introduces a unified Secret Enclave Vault, Four-Eyes Maker-Checker Governance, and Isolated Network Enclaves to guarantee that even on a developer workstation, infrastructure meets SOC 2 Type II, PCI-DSS v4.0 Requirement 3, and FIPS 140-2 Level 1/2 cryptographic compliance standards.

2 FIPS 140-2 Encrypted Secret Enclave (AES-256-GCM)

PortGrid uses Envelope Encryption. Every generated password, connection string, and TLS key is encrypted before touching host disk using authenticated symmetric encryption:

$$\mathcal{C}, \mathcal{T} = \text{AES-256-GCM}_{\mathcal{K}}(\mathcal{P}, \text{IV}, \text{AAD})$$
$\mathcal{P}$ Plaintext Secret: Database password, auth token, or encryption key.
$\mathcal{K}$ 256-bit Master Key: High-entropy cryptographic key derived via PBKDF2 stored at ~/.portgrid/portgrid.env (mode 0600).
$\text{IV}$ Initialization Vector (Nonce): 96-bit (12-byte) cryptographically secure random value generated fresh for every encryption operation.
$\text{AAD}$ Additional Authenticated Data: Service ID and timestamp bound mathematically to the ciphertext to prevent ciphertext transplant attacks.
$\mathcal{T}$ Authentication Tag: 128-bit GHASH authentication tag verifying that the ciphertext and AAD have not been modified by a single bit.

3 Mathematical Foundation of Galois/Counter Mode (GCM)

Galois/Counter Mode combines standard AES Counter Mode (CTR) for confidentiality with polynomial evaluation over the finite field $\text{GF}(2^{128})$ for authenticity.

Galois Field Definition: $\text{GF}(2^{128})$

Elements in the field are represented as binary polynomials of degree strictly less than 128. Field multiplication is defined modulo the NIST standard irreducible polynomial $f(x)$:

$$f(x) = x^{128} + x^7 + x^2 + x + 1$$

The GHASH Universal Hash Function

Let $H = \text{AES}_{\mathcal{K}}(0^{128})$ be the hash subkey. For blocks $X_1, X_2, \dots, X_m \in \text{GF}(2^{128})$, the GHASH function evaluates a polynomial in Horner form:

$$\text{GHASH}_H(X_1, \dots, X_m) = \sum_{j=1}^{m} X_j \cdot H^{m - j + 1}$$

The 128-bit authentication tag $T$ is computed by masking the polynomial evaluation with the encrypted initial counter block $J_0$:

$$T = \text{GHASH}_H(C) \oplus \text{AES}_{\mathcal{K}}(J_0)$$

If an attacker attempts to flip a single bit in the stored secret, the authentication tag evaluation fails during decryption with probability $1 - 2^{-128}$, instantly aborting container instantiation before invalid credentials can be injected.

4 PBKDF2 Key Derivation Mechanics

To prevent brute-force and dictionary attacks on master passwords, PortGrid employs RFC 8018 PBKDF2 with HMAC-SHA512:

$$\mathcal{K} = \text{PBKDF2}(\text{PRF}=\text{HMAC-SHA512}, \text{Password}, \text{Salt}, c = 600{,}000, \text{dkLen} = 32)$$

Each block $T_i$ of derived key material is computed as the XOR sum of $c$ successive HMAC evaluations:

$$T_i = U_1 \oplus U_2 \oplus U_3 \oplus \dots \oplus U_c$$
$$U_1 = \text{HMAC-SHA512}(\text{Password}, \text{Salt} \parallel \text{INT}(i)), \quad U_k = \text{HMAC-SHA512}(\text{Password}, U_{k-1})$$

With $c = 600{,}000$ iterations (exceeding OWASP 2024 recommendations), calculating a single candidate password requires hundreds of milliseconds on modern hardware, rendering GPU-accelerated brute-force attacks economically and computationally impossible.

5 Four-Eyes Maker-Checker Governance Policy

In enterprise banking systems, the Four-Eyes Principle mandates that any critical transaction or destructive modification must be approved by at least two distinct individuals: a Maker (initiator) and a Checker (approver).

Cryptographic State Machine

When Four-Eyes mode is active, high-risk actions (volume purge, master key rotation, production sync) cannot execute immediately. They traverse a formal state machine:

$$S_{\text{IDLE}} \xrightarrow{\text{Propose}(u_{\text{maker}}, \text{action})} S_{\text{PENDING}}$$
$$S_{\text{PENDING}} \xrightarrow{\text{Approve}(u_{\text{checker}}, \text{signature})} S_{\text{APPROVED}} \quad (\text{Enforced: } u_{\text{maker}} \neq u_{\text{checker}})$$
$$S_{\text{APPROVED}} \xrightarrow{\text{Execute}()} S_{\text{EXECUTED}} \implies \text{CommitToMerkleLedger}()$$
MAKER INITIATION (STEP 1)

Operator submits a mutation request (e.g. deleting PostgreSQL volume). PortGrid generates a cryptographic ticket ID: Ticket: tkt-7f8a12 (Status: PENDING_APPROVAL)

CHECKER APPROVAL (STEP 2)

Second authorized operator reviews the ticket in the Web Console or CLI and applies approval. Both cryptographic identities are committed into the Merkle audit chain.

6 Isolated Network Enclaves & Loopback Hardening

PortGrid enforces physical host network isolation by separating inter-container transport from developer access:

1. STRICT 127.0.0.1 BINDING

All exposed host ports (5432, 6379, 9092, 3000) bind strictly to 127.0.0.1. Zero sockets listen on 0.0.0.0, completely shielding local engines from Wi-Fi LAN scans.

2. INTERNAL BRIDGE NAMESPACE

Companion admin consoles (pgAdmin, Mongo Express, AKHQ) communicate with their database engines over a dedicated internal network namespace (portgrid-net) via private DNS names.

3. NO PRIVILEGE ESCALATION

Containers are spawned with kernel flag --security-opt no-new-privileges, preventing internal processes from acquiring root elevation or breaking out of user namespaces.
